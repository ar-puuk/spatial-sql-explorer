# Implementation Plan: Large Files and Viewport Loading

**Branch**: `007-viewport-loading` | **Date**: 2026-10-11 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `/specs/007-viewport-loading/spec.md`

## Summary

Make large files first-class. The viewer stops copying whole files into the
engine and stops holding the displayed result as one in-memory feature array.

**The engine reads the file in place.**
- **Web**: the picked `File` is registered as a lazily read handle.
- **VS Code**: the extension host serves the file from a loopback range
  server, reached as `localhost.`. The trailing dot sidesteps VS Code's webview
  service worker, which stalls worker requests to `localhost` (research §3).
  This also removes the base64 transfer that made a 50 MB GeoJSON take more
  than 45 s.

**Each format gets a measured read mode.**
- **GeoParquet/Parquet** are read in parts. Facts come from the footer, and
  views use bbox covering columns or a one-scan bbox index.
- **FlatGeobuf** is read in parts for facts and small views. It is loaded into
  memory for whole-file work.
- **Whole-read formats** are parsed once into a table with an R-tree. Above
  100 MB the read is announced first.
- **PMTiles** is view-only, through the `pmtiles` library on the map.

**Everything the user sees becomes a query over the result.**
- **Map**: features in view, capped, grid-thinned when over the cap, and
  refreshed on pan or zoom.
- **Table**: pages of rows, sorted in SQL.
- **Styles**: statistics computed in SQL.
- **Export**: unchanged.
- **Queries**: the default query loses its `LIMIT 1000`, and spec 002's
  50,000-row prompt goes away (FR-009).

Every risky assumption was spiked first (research.md), and the spikes changed
the design:
- **The real memory ceiling is 3.1 GiB**, not ~512 MB.
- **VS Code workers can read in parts**, through `localhost.` with a 206
  answer to `HEAD`.
- **FlatGeobuf through a handle costs about 0.74 ms per feature**, so
  whole-file work needs it in memory.
- **The engine has `ST_AsMVT`**, but per-view queries are fast enough
  without tiles.

## Technical Context

**Language/Version**: TypeScript (strict), Svelte 5, as before.

**Primary Dependencies**:
- DuckDB-WASM 1.32.0 (v1.4.3) + spatial. Newly used:
  - `registerFileHandle` and `registerFileURL`;
  - `db.open({ filesystem })`;
  - `read_parquet(…, file_row_number)`;
  - `spatial_filter_box`;
  - R-tree indexes.
- MapLibre GL JS, Svelte 5, Vite, esbuild.
- **One new runtime dependency**: `pmtiles` (BSD-3-Clause, about 15 KB), for
  PMTiles only (research §8).
- **Node `http`** in the extension host. It is built in; no package.

**Storage**: none new. The source stays where it is. Indexes and materialized
results live in engine memory for the session.

**Testing**:
- **Vitest (core)**: read-mode catalog, viewport SQL (bbox predicates,
  thinning, cap), paging SQL, style statistics, result-model decisions, OOM
  recovery logic.
- **Playwright (web)**: the open flow per read mode on committed small
  fixtures, with a `?e2e=1` cap override that exercises thinning and paging
  on small data. Also the announcement and Cancel, PMTiles, accessibility,
  and the spec 001–005 suites.
- **`@vscode/test-electron`**:
  - the loopback server (Range, `HEAD` 206, token, `Origin` check, sidecars);
  - an open over `localhost.`;
  - the forced fallback to whole transfer;
  - parity with the web.
- **Scale and performance** (SC-001–SC-006), on `tests/.large-data`
  generated by `npm run large-data`, which needs a native DuckDB CLI (and GDAL
  for FlatGeobuf). These skip with a message when the data is absent, and are
  run and recorded locally, like spec 005's QGIS read-back.

**Target Platform**: VS Code desktop (Windows, macOS, Linux), and evergreen
browsers for the web app. vscode.dev and remote hosts use the fallback until
verified.

**Project Type**: the existing monorepo (`apps/web`, `apps/vscode-ext`,
`packages/core`, `packages/ui`).

**Performance Goals**: SC-001–SC-005. Spiked values on 762 MB / 1.45 GB:

| Target | Spiked |
|---|---|
| Facts in ≤ 5 s | under 0.1 s |
| A view in ≤ 2 s | 0.04–0.3 s for GeoParquet |
| Cancel in ≤ 3 s | 0.1 s for queries |
| No task ≥ 1 s | |

**Constraints**:
- **Memory**: 3.1 GiB engine memory per webview (measured).
- **Lockdown**: the spec 002 lockdown stays. Only `/se-source/` is
  registered. User SQL still can't reach URLs, and the loopback URL is
  reachable only through the registered path.
- **CSP**: `connect-src` gains `http://localhost.:*`.
- **Single-threaded engine**: one query at a time per viewer. View, page and
  style queries are serialized and cancellable on the session's connection.

**Scale/Scope**:
- Files up to several GB for read-in-parts formats.
- Whole-read formats up to what fits in 3.1 GiB after parsing (about 2–4×
  the file size).
- 4M-row results in the table.

## Constitution Check

*GATE: passed before Phase 0 and re-checked after Phase 1 design.*

| Principle | Status | How this plan complies |
|---|---|---|
| I. Scope Discipline | ✅ | LOOK at large files, with QUERY, STYLE and EXPORT preserved. No editing, rasters, remote sources or sessions. PMTiles is view-only. |
| II. Host-Agnostic Core | ✅ | Read modes, view, page and statistics SQL, and the result model are in `packages/core`. The shells provide bytes through `HostAdapter.getFileSource`, which returns an opaque handle, a URL or bytes, and the new `readRange`. Core never touches `File`, `fetch` of user files, or IndexedDB; the lint rule still applies. The loopback server lives in `apps/vscode-ext`. |
| III. Native VS Code Feel | ✅ | Open progress and the read notices use the existing theme-token components. Status bar facts come from the whole file. |
| IV. Local-First | ✅ | The server binds loopback only, has per-document unguessable tokens and an `Origin` check, and serves opened files only. No data leaves the machine. |
| V. Bounded Resources | ✅ | This spec *is* this principle: the bbox and viewport queries with a cap that it requires. The memory figure is updated by measurement (3.1 GiB); the principle text cites omx-viewer's 512 MB as an observation, and this plan doesn't change the principle. OOM recovery re-registers the source. |
| VI. Verified Claims | ✅ | Every read mode was measured in both shells (research §2–§4). PMTiles and Remote-SSH are listed as unverified, with gates: a test before listing, a probe and fallback at runtime. |
| VII. Accessibility | ✅ | Progress, the announcement dialog, the notices and paged rows are announced, keyboard-reachable and axe-checked. |
| VIII. Clean-Room | ✅ | The server follows the HTTP Range RFC 7233. `pmtiles` is used as a dependency (permissive), not copied. |
| IX. Testing | ✅ | Unit, browser and extension suites, plus recorded local scale runs. |
| X. Simplicity | ✅ (justified) | One dependency (`pmtiles`) and one host mechanism (the loopback server); see Complexity Tracking. Vector tiles were deferred to avoid a second rendering path. |

**Post-design re-check**: no violations. The two additions are justified
below.

## Spec amendments made during planning

None to requirements. The planning outcomes are in research.md:

**Structure Decision**: the existing layout. Two new core folders: `source/`
(how the engine gets bytes) and `view/` (the SQL the map, table and styles
run). Shell changes are limited to delivering bytes: a handle on the web; the
loopback server and fallback in VS Code.

## Delivery order (vertical slices)

1. **Foundation**:
   - the engine filesystem config;
   - `FileSource` kinds;
   - the loopback server and its probe and fallback;
   - the read-mode catalog;
   - the result model with hidden columns.
2. **US1 + US2 (P1) on GeoParquet**:
   - facts first;
   - view queries with the cap and thinning;
   - the map rendering views;
   - notices;
   - selection outside the view.

   This is the MVP.
3. **FlatGeobuf in parts**: header facts and small-cap views.
4. **US3 (P2)**:
   - paged table and SQL sort;
   - the count-then-materialize result model;
   - style statistics in SQL;
   - the 50,000 prompt and `displayLimited` removed;
   - FlatGeobuf "load for queries".
5. **US4 (P2)**: whole-read formats.
   - parse into a table with an R-tree, through the handle or URL;
   - the 100 MB announcement, progress, Cancel and OOM recovery.
6. **US5 (P3)**: PMTiles, view-only.
7. **Polish**: scale runs (SC-001–SC-006), accessibility, screenshots, docs.

## Complexity Tracking

| Addition | Why needed | Simpler alternative rejected because |
|---|---|---|
| Loopback HTTP server in the extension host | Workers in VS Code webviews can't read the resource host (the service worker stalls them for 30 s); range reads need a URL the worker can reach. | Whole-file `postMessage` is what fails today (FR-003). A sync bridge needs `SharedArrayBuffer`, which isn't available. |
| `pmtiles` dependency | PMTiles is listed in CLAUDE.md and the spec (US5), and the engine can't read it. | Writing our own PMTiles reader duplicates a small maintained reference library. |
